## 1. 产品定义

一句话：**把模糊的研究想法，变成一份可直接写进论文的参考文献清单。**

面向学生与研究者的文献检索服务。用户不需要会想关键词，只需要说出自己想研究什么。

目标流程：

```
用户输入想法（自然语言）
    ↓
Agent 拆解意图 → 给出若干候选研究方向
    ↓
用户选择方向（可补充细节）
    ↓
Agent 多源检索 → 筛选 → 评估
    ↓
交付四件套：
  ① 论文本体（下载 / 原文链接）
  ② 选择理由（为什么推荐这篇）
  ③ 引用格式（GB/T 7714-2015 等）
  ④ 可写入正文的引用内容（这篇能支撑你论文里的哪句话）
```

其中 ④ 是与所有现有工具的核心差异点。Google Scholar 给你论文，Zotero 帮你管论文，
但没有工具告诉你"这篇论文的哪个结论，可以怎么写进你的第三章"。

### 1.1 明确不做的事

- 不做文献管理器（Zotero 已经足够好，我们做它的智能入口）
- 不做论文写作助手（范围过大，且触碰学术诚信红线）
- 不做学术社交 / 笔记标注
- 不代替用户判断。所有 AI 结论必须给出依据，用户保留最终决定权

值得单独强调的两个工程细节，它们是踩过坑才有的代码，不要在新项目里重新踩：

1. **来源分级**。代码里把数据源分成 `FORMAL_CITATION_SOURCES = {semantic_scholar, crossref, openalex}`
   和 `DISCOVERY_HINT_SOURCES = {arxiv, anysearch_academic}`。后者只能用来"发现线索"，
   不能作为正式题录来源。这个区分直接决定了引用的可信度。
2. **DOI 内容协商的编码处理**。`_response_bibliography_text` 按 utf-8 → 响应声明 → gb18030
   顺序试解码，因为 DOI 服务经常返回 UTF-8 却不声明 charset。中文题录尤其容易踩。

| 现有实现                                 | 问题                                                                        | 新项目方向                          |
| ---------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------- |

| `literature_scheduler.py` 的配额调度     | 目标是"填满 zh=8/en=5 的名额"，满额即停                                     | 目标改为"排序与解释"，见 §3         |

### 2.3 完全没有的部分（净新增）

- 意图拆解与方向推荐（现有系统的检索词来自"已确认的项目模型"，不是用户的自由描述）
- 相关性评分与排序
- 推荐理由生成

## 3. 一个必须正视的架构差异

这是本稿最重要的一条判断，会影响后续所有设计。

现有系统是**补全引擎**，新产品需要的是**发现与排序引擎**。两者的目标函数不同：

|          | workflow_bundle（补全）                                                 | academic-search（发现） |
| -------- | ----------------------------------------------------------------------- | ----------------------- |
| 成功定义 | 凑满配置的中英文篇数                                                    | 找到最值得读的那几篇    |
| 终止条件 | 配额满足即停止检索                                                      | 检索到边际收益递减      |
| 候选处理 | 够数了就丢弃剩余（代码里确实有 `quota_satisfied_unprocessed` 这个状态） | 全部参与排序            |
| 评估输出 | 收 / 不收                                                               | 多维得分 + 排序 + 理由  |
| 并发上限 | `MAX_DISCOVERY_WORKERS = 2`、`SEARCH_RESULT_LIMIT = 3`（够用即止）      | 需要更宽的召回          |

含义：**调度器不能直接复用，必须重写**。但它的确定性编排思想要保留——
现有代码的注释写得很清楚，模型只负责"查询词措辞"和"语义判断"，
工作流选择、provider 轮转、排队、终态都由确定性代码控制，不交给大模型的 tool-calling 循环。
这个设计在 SaaS 场景下更有价值：可预测、可计费、可复现、可审计。

## 4. 前端：完全重做，零复用

结论已定：**不复用 `workflow_bundle/webui`，前端全部重新设计与实现。**

### 4.1 现状实测

技术栈本身不算旧（React 19 + antd 6 + Vite 8 + TypeScript），问题在于工程结构：

```
webui/src/  —— 整个前端只有 6 个文件
  App.tsx     8316 行   361 KB    ← 单文件承载全部界面
  App.css     4419 行    75 KB    ← 单文件承载全部样式
  types.ts    1224 行     30 KB
  api.ts       351 行     15 KB
  index.css     23 行
  main.tsx      11 行
```

没有组件目录、没有路由、没有状态管理层、没有设计系统、没有前端测试。
8316 行的单文件组件意味着任何改动都要在一个巨型文件里搜索定位，无法并行开发，无法复用，
也无法为新产品的对话式交互提供任何基础。

除结构问题外，还有两个具体的可用性债务（来自实际驱动浏览器做验收时的记录）：
antd 的 Upload 组件会打开原生文件选择框导致自动化点击超时；
Tab 切换后 DOM ref 失效需要重新定位。这些说明交互层缺乏可测试性设计。

### 4.2 新产品的界面形态与旧界面根本不同

这是"必须重做"而不是"最好重做"的原因：

|          | workflow_bundle 前端                | academic-search 前端           |
| -------- | ----------------------------------- | ------------------------------ |
| 交互范式 | 表单 + 分步审核确认                 | 对话式引导 + 渐进披露          |
| 核心页面 | 工作区管理、材料上传、逐阶段 review | 搜索入口、方向选择、结果卡片流 |
| 状态模型 | 长期工作区状态机                    | 短生命周期搜索会话             |
| 实时性   | 轮询任务状态                        | 检索进度流式推送               |
| 用户画像 | 单人、重度、愿意学习流程            | 首次访问即需理解，零学习成本   |
| 视觉要求 | 内部工具，够用即可                  | 面向公众的产品，设计即竞争力   |

旧界面是给"知道自己在做什么的单个操作者"用的内部工具。
新产品的用户第一次打开就要能用，界面本身就是转化率的一部分。

### 4.3 新前端的设计原则（待细化）

1. **搜索框是唯一入口**。首屏不做功能罗列，就一个输入框加一句引导文案
2. **渐进披露**。方向选择、评估维度、引用内容按需展开，不一次性堆给用户
3. **等待即价值展示**。检索需要时间，进度过程要显示"正在查哪些源、找到多少篇、筛掉多少"，
   让用户看到系统正在完成的工作，建立结果可信度
4. **结果卡片是核心组件**。四件套（论文 / 理由 / 引用格式 / 可写入内容）在一张卡片内分层呈现，
   默认只显示标题与理由摘要，展开看细节
5. **一键复制优先于下载**。用户的真实动作是"把引用粘到 Word 里"，不是"下载文件到本地"

### 4.4 前端技术栈（当前选择）

> 本节的设计系统细节已展开为独立文档：[`02-frontend-design-system.md`](02-frontend-design-system.md)。
> 那里记录了用 `ui-ux-pro-max` 技能库检索后的风格、配色、字体决策与取舍理由。

面试作品采用 Vue 生态，理由是既能展示 TypeScript 工程能力，也能与 Python 后端形成清晰边界：

- 框架：Vue 3 + TypeScript
- 样式：Tailwind CSS（避免再出现 4419 行的单体 CSS）
- 组件：优先 Vue 的 headless 方案（Reka UI / shadcn-vue）而非 antd，
  因为面向公众的产品需要自有视觉语言，antd 的默认观感辨识度太低
- 状态：TanStack Query 的 Vue 适配器管理服务端状态；Pinia 管理输入草稿、卡片展开等轻量客户端状态
- 构建：Vite
- 实时：SSE（检索进度是单向推送，不需要 WebSocket 的双向能力）
- 类型契约：FastAPI 输出 OpenAPI，由前端生成 TypeScript API 类型，避免两端手写重复 DTO

强制约束，写进项目规范：
单文件不超过 300 行；必须有组件目录与路由分层；关键交互必须可被自动化测试驱动。

未决问题：

- 是否需要服务端渲染（影响 SEO，而 SEO 对这类工具的自然流量可能很重要）
- 移动端优先级。学生用手机查文献的场景存在，但复制引用到论文里显然是桌面场景

## 5. 评估维度设计（待确认）

排序需要分数。初步提议五个维度，其中前两个决定排序，后三个用于展示与筛选：

```
relevance    0-100   与用户意图的匹配度        ← 主排序键
quality      A/B/C/D 期刊会议等级、引用数、作者影响力  ← 次排序键
utility      高/中/低 有无实现细节、开源代码、实验数据
recency      年份 + 是否综述
accessibility 全文可获取性、语言、篇幅
```

未决问题：

- `quality` 的数据从哪来？引用数 Semantic Scholar 有，期刊分区需要额外数据源（JCR / 中科院分区 / CCF 列表）
- `utility` 只靠摘要判断会不准，靠全文判断成本高。是否只对 top N 做？

## 6. 文献研究与 RAG（新增核心能力）

检索结果不是终点。用户选定值得研究的文献后，应能将这些文献纳入一个研究集合；系统解析、向量化并建立可追溯的索引。后续研究 Agent 围绕该集合回答问题、比较观点、梳理研究脉络，而不是凭模型记忆生成答案。

### 6.1 产品边界

RAG 的职责是**找回证据**，不是宣称“向量库里的内容就是真实信息”。Agent 的职责是基于找回证据进行归纳，并明确说明证据不足或文献存在分歧的情况。

每一个涉及研究事实、方法、结果或结论的回答必须带有：

- 论文题名与作者/年份
- 可访问的原文链接
- 被引用的原文片段
- 页码或章节等定位信息；无法可靠定位时明确标注

无法从已索引文献中得到支持时，Agent 必须回答“现有文献不足以支持该结论”，不能用自身知识补全为确定事实。

### 6.2 用户流程

```
搜索并得到排序后的文献
    ↓
用户选择文献，核验 DOI 题录
    ↓
系统取得并校验允许处理的全文 / 用户上传有权处理的 PDF
    ↓
原子创建研究集合关联、文献文件与入库任务，解析并异步建立索引
    ↓
用户提出研究问题，例如“这几篇论文对 X 的结论是否一致？”
    ↓
Agent 混合检索相关片段 → 重排序 → 基于证据作答并逐条引用
```

研究问答应支持：单篇论文问答、跨论文比较、方法/数据集/结论提取、观点一致与冲突分析、按主题形成带引用的研究笔记。它不代替用户写作，也不输出没有证据支撑的结论。

### 6.3 索引与检索要求

- 仅索引同时具备已核验 DOI 与已取得正文的文献；正文只可来自开放获取直链、后续配置的官方许可来源或用户有权上传的文件，且不绕过版权限制。
- 首版自动获取与解析只支持 PDF；后续的 HTML / DOCX 解析仍按标题和段落等文档结构切块，而非固定字符截断；每个块保留文献、页码、章节、URL、解析版本和处理时间等元数据。
- 文献采用 L1 章节、L2 小节/段落组、L3 叶子片段的父子分块；初始只召回 L3，当同一父块有多个命中时上卷合并上下文后再精排。
- 中英文混合语料使用多语言 embedding；查询采用向量检索 + 关键词/BM25 检索 + 研究集合元数据过滤，经 RRF 融合、父块合并与 Reranker 重排序后再生成回答。
- 首次检索后先结构化评估证据是否足够，路由为回答、一次 Step-back/HyDE 改写、请求用户澄清、范围选择或证据不足拒答；改写文本只用于检索，不得成为回答证据。
- 索引为异步任务，向用户显示解析、切块、嵌入、完成或失败状态；低质量解析的 PDF 不能伪装成可可靠问答的文献。
- 用户、研究集合、文献、文档版本、片段、索引版本和问答记录必须隔离并可追溯；文献更新或重新解析后应使旧向量失效并重建。

### 6.4 MVP 技术取舍

为完整展示 RAG 向量检索架构，首版使用 Milvus 保存文献片段的向量索引；PostgreSQL 仍是用户、研究集合、文献版本、权限、任务、问答和引用关系的唯一业务真相来源。Redis 用于任务队列、缓存、限流和 SSE 事件；PDF 原文件与解析产物放 MinIO/S3 兼容对象存储。

Milvus 只保存向量与必要的索引字段（如 `chunk_id`、`document_id`、`collection_id`），不能成为权限或文献元数据的唯一来源。检索时先按研究集合过滤，再由 PostgreSQL 校验访问权限。

RAG 质量至少追踪三类指标：检索命中率（正确证据是否进入 top-k）、引用可定位率、回答受证据支撑率。没有这些评估，RAG 只会把幻觉变得更像“有依据”。

## 7. 成本结构与定价（MVP 不做付费功能）

成本是这个产品的生死线。三段式分层是控制成本的核心手段：

```
第一层 元数据过滤    确定性代码，零 LLM 成本    数百篇 → 数十篇
第二层 标题摘要评估  便宜模型批量处理           数十篇 → 15 篇
第三层 全文深度分析  强模型，仅对用户主动研究的文献  用户按需触发
```

单次搜索的粗略成本（需要实测校准，以下仅为量级估算）：

| 环节         | 成本量级                                         |
| ------------ | ------------------------------------------------ |
| 意图拆解     | 一次强模型调用                                   |
| 批量评估     | 十几到几十次便宜模型调用                         |
| 引用内容生成 | 每篇一次长上下文调用，最贵                       |
| RAG 入库     | 用户加入文献时的全文解析、切块与 embedding 成本  |
| RAG 问答     | 每次提问的混合检索、重排序与基于上下文的回答调用 |
| 学术 API     | 多数免费但有限速，需要备用付费通道               |
| 基础设施     | 服务器 / 数据库 / 对象存储                       |

已定：**MVP 不接支付、不设付费墙或用户付费额度**。引用内容生成（④）仍保留为受控的单篇能力，用于验证核心价值；成本通过服务端限流、单用户每日上限和全局预算熔断控制，而不是向用户收费。

RAG 只索引用户主动加入研究集合的文献，不能自动向量化所有检索结果；入库和问答分别设置单用户与全局预算上限。

后续验证到稳定需求与单位成本后，再决定是否引入按次、订阅或混合定价。届时 ④ 仍是最自然的可付费能力，但这不应阻塞当前 MVP。

当前不做的事：

1. 不设计按次、订阅或混合定价
2. 不接支付、订单、订阅、退款等商业化链路

仍需决定：

1. 为防止滥用，单用户每日可触发多少次深度生成
2. 是否用自部署开源模型压成本（省钱但增运维）

## 8. MVP 范围（待确认）

第一版必须有：

- 搜索会话与基础滥用保护（账户体系和商业额度控制可后置）
- 意图拆解 → 方向选择（先做单轮，不做多轮对话）
- 多源检索：OpenAlex + Semantic Scholar + arXiv + CrossRef（中文源第二版再说）
- 两阶段评估（元数据过滤 + 摘要评估）
- 相关性排序 + 推荐理由
- GB/T 7714-2015 引用格式
- 全新前端：搜索入口 + 方向选择 + 结果卡片流 + 检索进度实时显示（不复用旧 webui）
- 研究集合：仅将 DOI 已核验且正文已成功取得、校验的文献加入集合并完成异步索引
- 基于研究集合的证据问答：每个结论附原文片段和来源定位

第一版推迟：

- 可写入正文的引用内容生成（成本高，但这是核心卖点——**需要讨论是否值得提前**）
- 出版商落地页爬取、付费墙处理、HTML / DOCX 自动获取与解析
- 个人文献库
- 批量导出（BibTeX / EndNote）
- 团队协作

关于推迟 ④ 的矛盾，我的看法：如果 MVP 不含 ④，产品就退化成"一个更好的 Semantic Scholar"，
差异化不足，很难验证真实需求。建议 MVP 保留 ④ 的**简化版**——
只对用户明确点选的单篇论文生成，一次一篇；当前免费但受服务端限流和预算控制。这样既能验证需求，又不会让成本失控。

## 9. 必须解决的风险

| 风险             | 说明                                     | 应对方向                                                                           |
| ---------------- | ---------------------------------------- | ---------------------------------------------------------------------------------- |
| 全文获取的合法性 | 大量论文有版权限制                       | 首版仅从明确开放获取的直链 PDF 受控下载，或接收用户有权上传的文件；不爬落地页、不绕过限制、不碰盗版镜像 |
| 学术诚信边界     | ④ 生成"可写入的句子"容易被当成代写       | 必须强制携带引用标注；生成的是"如何引用他人观点"，不是"替你写论文"；界面上明确提示 |
| AI 评估不可靠    | 推荐理由可能是幻觉                       | 理由必须引用原文片段作为依据，不允许无出处断言；收集用户反馈做闭环                 |
| RAG 回答失真     | 检索遗漏、PDF 解析错误或模型脱离证据总结 | 每个结论附证据片段与定位；证据不足时拒答；记录检索与引用质量指标                   |
| 用户资料隔离     | 用户上传文献或研究问题可能敏感           | 按用户与研究集合做访问控制和索引隔离，不跨集合召回内容                             |
| API 限速与稳定性 | 免费学术 API 随时可能变                  | 复用 `literature_rate_limit.py`；多源冗余；结果缓存                                |
| 中文文献覆盖     | 开放中文学术源质量参差                   | 第二版评估 CNKI 等付费源；初期以英文为主                                           |

其中"学术诚信"这条不只是合规问题，也是产品设计问题。
④ 的正确形态是**教用户如何引用**，而不是**替用户写作**。
文案、界面、生成内容的形式都要体现这一点。

## 10. 推荐技术架构（面试作品方向）

技术架构选择以“能完整展示工程、RAG 与 Agent 设计能力，同时可在本地一键运行”为目标。采用**模块化单体 + 异步 Worker + 独立向量检索服务**，不在首版把业务拆成多个难以维护的微服务。

```text
Vue 3 + TypeScript 前端
          |
FastAPI API（REST + SSE）
     |         |
PostgreSQL    Redis
业务真相      队列 / 缓存 / 限流 / 事件
                 |
      Python Worker（LangChain + LangGraph）
        |          |            |
   学术数据源     Milvus      MinIO / S3
                 向量索引      原文与解析产物
```

### 10.1 组件职责

| 组件       | 技术                                | 职责                                                                            |
| ---------- | ----------------------------------- | ------------------------------------------------------------------------------- |
| Web        | Vue 3 + TypeScript + Vite           | 搜索、方向选择、进度、文献结果、研究集合与证据问答                              |
| API        | Python + FastAPI                    | 鉴权、参数校验、创建任务、读取结果、SSE 推送；不执行长耗时任务                  |
| Worker     | Python                              | 多源检索、题录补全、文档解析、嵌入、LangGraph 运行与失败重试                    |
| Agent 框架 | LangChain + LangGraph               | LangChain 封装模型、文档和检索能力；LangGraph 编排可恢复的受限工作流            |
| 关系数据库 | PostgreSQL                          | 用户、搜索会话、研究集合、文献元数据、权限、任务、问答、引用与图状态 checkpoint |
| 缓存与队列 | Redis                               | 异步队列、缓存、provider 限速、使用上限和 SSE 事件分发                          |
| 向量数据库 | Milvus                              | 文献片段 embedding 与相似度检索，不保存业务真相                                 |
| 对象存储   | MinIO（本地）/ OSS、COS、S3（部署） | PDF、HTML、DOCX、解析文本与页级衍生文件                                         |
| 部署       | Docker Compose                      | 在本地统一启动前端、API、Worker 与所有状态服务                                  |

前后端接口以 OpenAPI 为唯一契约，由 FastAPI 生成定义并在 Vue 端生成 TypeScript 类型。业务不维护两份手写 DTO。

PostgreSQL 的实体、字段、索引与外部存储边界见 [`09-database-design-discussion.md`](09-database-design-discussion.md)。

### 10.2 两条异步业务链路

```text
文献入库：
加入研究集合 -> Redis 任务 -> 全文合法性校验 -> 解析
-> 结构化切块 -> embedding -> Milvus 入库 -> PostgreSQL 更新状态 -> SSE

研究问答：
用户提问 -> 创建执行任务 -> LangGraph Worker 运行
-> Milvus 向量检索 + 关键词检索 + 元数据过滤 -> 重排序
-> 证据核验 -> 写入回答与引用 -> SSE 推送前端
```

API 请求只创建并查询任务，刷新页面后由 PostgreSQL 恢复真实任务状态。Redis 不是长期业务状态的唯一存储。

### 10.3 Agent 工作流边界

Agent 不管理权限、provider 调度、限流、题录格式和任务状态；这些均为确定性代码。LangGraph 只在需要语义理解、跨文献归纳和证据判断时介入。

```text
SearchGraph：
意图解析 -> 查询计划 -> 确定性多源检索 -> 规则过滤
-> 批量语义评分 -> 确定性排序

ResearchGraph：
问题路由
  -> 简单问题：Hybrid 召回 -> 父块合并 -> 精排 -> 证据路由 -> 带引用回答 / 澄清
  -> 复杂问题：Plan-and-Solve -> 受限 ReAct 取证
             -> Evidence Reflection 核验 -> 综合回答
```

复杂研究任务以 Plan-and-Solve 为主范式：先拆解有限的可验证子问题；受限 ReAct 只负责有限次数的检索工具调用；Reflection 节点必须读取原文证据，检查结论是否被片段支持。任何未通过核验的事实不得进入最终回答。

### 10.4 数据与权限边界

- PostgreSQL 记录用户、研究集合、文献版本和访问规则；Milvus 仅用 `collection_id` 等字段进行预过滤。
- 每次向量检索都限定当前研究集合，并由 PostgreSQL 二次校验文献权限。
- 原始文件不放 PostgreSQL 或 Milvus；对象存储中的文件使用私有路径和受控访问。
- 文献更新、重新解析或删除时，相关片段、向量和缓存必须按版本失效。
- 所有研究结论保存其论文、片段、页码/章节和模型/图版本，以支持审计与复现。

### 10.5 Docker Compose 服务

本地开发 Compose 只管理有状态服务；Vue、FastAPI 与 Worker 在宿主机启动，以保留热更新和断点调试体验：

```text
postgres   PostgreSQL
redis      Redis
etcd       Milvus 元数据服务
milvus     Milvus 向量检索服务
minio      本地开发与演示用 S3 兼容对象存储
```

MinIO 仅限本地开发和面试演示，不作为生产长期依赖；生产环境保持 S3 兼容接口并直接使用阿里云 OSS、腾讯云 COS 或其他托管对象存储。MinIO 中的应用文献与 Milvus 内部数据必须分到不同 bucket。

该形态在面试中能直观展示：前后端分层、异步任务、RAG 入库、Milvus 检索、LangGraph 工作流、状态持久化与可复现的本地环境。

职责约束如下：

- `frontend/features` 按产品功能收敛，通用组件只放入 `components`；请求数据由 TanStack Query 管理，Pinia 不复制服务端数据。

- `rag` 管理文献入库、检索、证据和评测；`agents` 只保留 LangGraph 图与节点。图通过模块服务调用检索和证据能力，不能绕过权限、版本及审计边界。
- `workers` 执行 PDF 解析、向量化、索引、重试和长耗时研究任务；状态写入 PostgreSQL，通知和短期协调使用 Redis，不能依赖 API 进程内存。
- `infra` 与 `scripts` 仅保留部署和运维资源，避免把业务代码放入 Docker/Compose 脚本中。

## 11. 下一步：需要你决定的问题

按优先级排列：

1. **MVP 是否包含 ④（可写入引用内容）**，包含的话是全量生成还是用户点选单篇生成？
   （我的建议：单篇生成的简化版，免费但受服务端限流和预算控制）
2. **目标用户优先级**：本科毕业论文 / 研究生科研 / 企业研发？三者的研究流程、功能深度和可接受等待时间差别很大
3. **MVP 成本上限**：单用户每日深度生成次数与全局日预算各是多少？（暂不做定价和付费功能）
4. **架构确认**：前端 Vue 3 + TypeScript；后端 Python FastAPI；LangChain + LangGraph；
   PostgreSQL + Redis + Milvus + MinIO/S3；Docker Compose。还需确认是否需要 SSR
5. **视觉风格方向**：前端既然重做，需要先定调性——工具型的克制清爽，还是内容型的杂志感？
   这个定下来才好动手做界面
6. **开发资源**：独立开发还是有协作者？这决定 MVP 的合理切分粒度
7. **RAG 准入规则已定**：MVP 仅自动获取明确开放获取的直链 PDF，同时支持用户上传有权处理的 PDF；没有 DOI 或未能取得、校验正文的候选不进入长期库。

其余待决定问题会在对应模块实现前继续细化。
