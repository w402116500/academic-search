# academic-search RAG 文献研究讨论稿

状态：进行中；研究集合准入、开放获取直链 PDF 下载暂存、准入与集合构建 API、PDF 入库 Worker 及 Milvus L3 向量写入已实现；RAG 检索、证据组装与研究对话 Agent 尚未实现。
定位：定义用户获得文献后，如何将选定文献变成可检索、可引用、可比较的研究集合。
关联：检索结果入口见 [`03-literature-search-and-discovery-discussion.md`](03-literature-search-and-discovery-discussion.md)；运行治理见 [`06-session-reliability-and-governance-discussion.md`](06-session-reliability-and-governance-discussion.md)。

## 1. 产品定位

RAG 不是一个脱离文献来源的普通聊天框。它的职责是从用户选定的文献中找回证据片段，让 Agent 围绕这些证据完成研究辅助。

向量检索结果不是事实本身，论文原文才是证据来源。Agent 可以归纳、比较和指出冲突，但不能将模型自身记忆伪装成已被文献支持的结论。

## 2. 用户流程

```text
用户从检索结果中选择文献
  -> DOI 题录核验通过
  -> 系统取得并校验允许处理的全文，或接收用户上传文件
  -> 原子创建研究集合关联、文献文件与入库任务
  -> 异步解析、结构化切块、嵌入与建立索引
  -> 用户提出研究问题
  -> 混合检索相关证据、重排序
  -> Agent 生成带逐条来源定位的回答
```

研究集合是 RAG 的边界。问答只能从当前集合及用户明确允许的范围召回内容，不能跨集合隐式混入其他用户或其他课题的资料。

## 3. 文献入库与索引

### 3.1 可处理文献

RAG 的准入条件是“已核验 DOI + 已实际取得的合法正文”，两者缺一不可。没有 DOI、题录存在冲突或缺失、只有落地页、只有未经验证的 URL，或不能取得合法正文的候选，均不进入研究集合和向量库。

首版仅处理以下两类 PDF：

1. Provider 明确标注为开放获取，且返回直接 PDF URL；系统下载、验证后保存。
2. 用户确认有权处理并主动上传的 PDF。

系统不爬取出版商落地页，不绕过登录、付费墙、验证码或访问限制，不作为第三方论文下载代理。后续可对已配置且明确许可的官方来源增加 `official_download`，HTML 与 DOCX 的获取、解析能力也放在后续版本。

自动下载必须是后端受控任务：只使用搜索会话中已发现的 URL，限制协议、重定向、下载大小和超时；阻断本地/私有网络目标；同时校验 HTTP `Content-Type` 与 PDF 魔数；流式计算 SHA-256。对象先以临时键上传；准入服务通过服务端复制将其转为正式对象，再创建数据库记录。对象存储与数据库之间使用补偿清理：任一步失败都删除本次可能遗留的正式键和暂存键。

下载校验通过后，系统在一个事务中写入 `papers`、`collection_papers`、`documents` 和初始 `ingestion_runs`；随后由 Worker 开始解析。这样数据库中的论文不是“有一条题录”，而是“已经拥有可追溯研究正文”的文献。当前 `ResearchCollectionAdmissionService` 已实现这一准入事务、工作区权限校验、同 DOI 幂等处理和对象补偿清理；`POST .../fulltext/admission` 会创建 `pending / parse` 入库运行。用户确认集合构建后，`POST /collections/{collection_id}/build` 才将活动运行转为 `queued` 并逐篇投递 arq；`app.workers.ingestion` 消费这些任务并完成 PDF 解析、切块、embedding 与 Milvus 写入。

解析失败、扫描件质量过低、页码无法定位等情况必须显式标注，不能让用户误以为该文献已经具备可靠问答能力。`documents` 创建成功不等于可被 RAG 回答，只有当前入库运行完成并且向量索引写入成功后才可检索。

### 3.2 三级结构化切块与父块合并

长期目标以标题、章节、段落、图表说明和参考文献区等文档结构为基础，不采用只按固定字符数截断的策略。当前 MVP 使用 `pypdf` 提取的页文本与空行段落作为可靠边界，再施加可配置字符预算；它会保留页码、段落编号、L3 重叠和父子 UUID，但暂不自动识别论文标题层级。

| 层级 | 学术文献中的对应结构 | 用途 |
|---|---|---|
| L1 | 大章节或完整论文主题区段，如方法、实验、讨论 | 回答需要较大上下文时的父块 |
| L2 | 小节或连续段落组 | 保留一个具体论证单元的上下文 |
| L3 | 可精确检索的叶子片段 | 写入 Milvus，作为初始召回目标 |

每个 L3 必须指向直接 L2 父块和所属 L1 根块。向量检索先只召回 L3；当同一 L2 或 L1 下有多个叶子片段命中时，系统以父块替换这些子块，再进入精排。这一 Auto-merging 机制解决“小片段命中准确但上下文不足”的问题，且只能在同一文献版本、同一研究集合内发生。

每个片段至少保存：

- 研究集合与文献标识。
- 用户与研究集合隔离字段，用于 Milvus 查询预过滤。
- 文档版本和解析版本。
- 原文文本、页码、章节标题和页内定位信息。
- 原文 URL、访问类型和处理时间。
- 嵌入模型与索引版本。
- `chunk_id`、直接父块 ID、根块 ID、层级与顺序编号。

重新解析或替换文档时，旧片段和旧向量应失效，避免同一论文的不同版本混合召回。

### 3.3 当前 Worker 入库实现

`app.modules.ingestion` 与 `app.workers.ingestion` 已实现以下受控链路：

```text
queued / parse
  -> 从 MinIO/S3 正式对象键流式下载到 Worker 临时目录
  -> pypdf 按页解析，记录空白页；全篇没有可提取文本时明确失败
  -> 页码与段落边界生成 L1 / L2 / L3，并把全部层级写入 PostgreSQL
  -> 仅读取 L3 调用 OpenAI 兼容 embedding
  -> Milvus 写入 chunk_id、隔离过滤字段与向量
  -> 原子切换旧 current 版本为 false，本次为 completed / current
```

Milvus 写入成功而 PostgreSQL 最终状态提交失败时，Worker 会按 `ingestion_run_id` 删除本次已写向量，再将运行标记为失败。解析、存储、嵌入或索引任一阶段失败都会记录稳定错误码和可展示错误信息；任务绝不会把扫描件或空文本 PDF 伪装为可检索文献。

## 4. 检索与回答链路

```text
用户问题
  -> 向量召回 + 关键词/BM25 召回 + 研究集合元数据过滤
  -> RRF 融合候选
  -> 同文献父块 Auto-merging
  -> Reranker 精排与阈值过滤
  -> 证据评分：回答 / 一次改写 / 请求澄清 / 拒答
  -> Agent 仅使用入选证据归纳回答
  -> 回答中的每项结论绑定具体证据与定位
```

中英文混合语料使用多语言 embedding。Hybrid 检索把向量相似度与关键词/BM25 召回通过 RRF 融合，随后对候选执行 Reranker 精排；精排前扩大候选池，精排后应用最低相关性阈值。检索结果需要保留召回分、RRF 排名、精排分、父块合并记录和最终引用片段，便于后续调试回答为何引用某篇文献。

每次查询必须以 `user_id`、`research_collection_id`、`document_version` 和叶子层级等条件过滤。Milvus 的过滤只是第一道边界，PostgreSQL 仍需在读取原文和生成回答前二次校验权限。

### 4.1 纠错检索与人工澄清

首次检索后先由结构化证据评分器判断 `relevance`、`answerability`、歧义类型和下一步路由：

| 路由 | 条件 | 行为 |
|---|---|---|
| `answer` | 证据足以回答 | 进入带引用的回答或研究分析 |
| `rewrite` | 有相关信号但证据不足 | 只允许一次 Step-back 或 HyDE 改写后重新检索 |
| `clarify` | 缺少研究对象、版本、条件等关键信息 | 请求用户补充信息并保存恢复状态 |
| `scope_select` | 多个论文或研究方向都可能相关 | 让用户选择范围后定向检索 |
| `no_knowledge` | 没有可靠证据 | 明确拒答，不用模型知识补全 |

HyDE 和 Step-back 只用于改善查询，不构成回答证据，也不能出现在最终引用中。查询改写达到一次预算后仍无法取得充分证据时，系统必须转为澄清或拒答，不能形成无界循环。

## 5. 研究功能

首版研究问答需要支持：

1. 单篇论文问答，例如论文的研究问题、方法、数据集、结论与局限。
2. 跨论文比较，例如不同论文是否得到相同结论、采用了何种不同方法。
3. 按主题提取多篇文献中的方法、变量、数据集和实验设置。
4. 识别一致观点、分歧观点以及造成差异的已知条件。
5. 形成带证据引用的研究笔记，供用户后续自行整理。

## 6. 多 Agent 研究分析

多 Agent 不是产品所有流程的默认实现。多源检索、provider 限速、权限控制、任务状态、题录格式化和结果排序都应保持确定性代码编排；它们需要可预测、可计费、可重试的行为，而不是自主 Agent 循环。

多 Agent 仅在问题需要跨论文、跨主题地收集和比较证据时启用，例如研究综述、方法对比、结论冲突分析和多篇文献共同支持某个问题的场景。

### 6.1 协作链路

```text
用户研究问题
  -> 研究规划 Agent：拆成可验证的子问题和检索维度
  -> 证据检索 Agent：为各子问题并行召回并重排序 RAG 片段
  -> 分析 Agent：提取方法、数据集、结论、限制等原子事实
  -> 证据核验 Agent：检查事实是否被原文片段真正支持
  -> 综合 Agent：仅基于已核验事实生成带引用的回答或研究笔记
```

每个中间 Agent 都必须输出结构化结果，而不是只返回一段自然语言。最小字段包括：子问题、结论或原子事实、证据片段 ID、论文 ID、定位信息、置信/证据充分性、未解决问题。综合 Agent 只能使用已通过核验的事实。

### 6.2 角色职责

| 角色 | 职责 | 不负责的事 |
|---|---|---|
| 研究规划 Agent | 将复杂研究问题拆成有限、可核验的子问题 | 自行断言研究结论 |
| 证据检索 Agent | 根据子问题调用混合 RAG 检索并返回候选片段 | 将检索分数解释为事实正确性 |
| 分析 Agent | 从片段中提取方法、数据、结果、限制和冲突线索 | 脱离片段补全论文内容 |
| 证据核验 Agent | 判断每项事实与片段是否蕴含一致，识别扩大解释或错误归因 | 用常识替代缺失证据 |
| 综合 Agent | 组织已核验事实，解释一致性、差异和证据不足 | 引入未核验的新事实 |

其中证据核验 Agent 是优先级最高的角色。它的价值不在于生成更多内容，而在于阻止“回答看似合理、引用却不支持结论”的错误。

### 6.3 启用规则与 MVP 范围

以下情况启用多 Agent 流程：问题包含多个独立维度、要求比较多篇论文、要求分析研究结论是否冲突，或要求生成结构化研究笔记。单篇论文的事实问答、简单题录查询和结果卡推荐理由继续走固定的 RAG 检索 -> 重排序 -> 带引用回答流程。

MVP 只实现两个显式 Agent 角色：研究规划 Agent 与证据核验 Agent。证据检索、事实提取和最终回答暂由确定性工作流加受限模型调用实现，并保留结构化输入输出，后续再根据质量和延迟数据拆分为独立 Agent。

每个多 Agent 请求必须设置最大子问题数、最大并发数、每角色超时和总 token/模型预算。任何一个子问题失败时，综合结果应标记缺口并继续返回已核验证据，不能由其他 Agent 静默猜测补齐。

## 7. 回答契约

每个涉及事实、方法、结果或结论的回答必须提供：论文题名与作者/年份、原文证据片段、可访问链接，以及页码或章节定位。无法可靠定位时必须明确说明。

以下情况应触发“证据不足”而不是猜测性回答：

- 当前研究集合中没有相关片段。
- 片段只支持相关主题，不能支持用户提出的具体断言。
- 不同文献的证据互相冲突，且系统无法从证据判断原因。
- 解析质量不足以支撑精确引用。

## 8. 技术方案与质量评估

MVP 使用 Milvus 保存文献片段 embedding 与向量索引；PostgreSQL 保存用户、研究集合、文献版本、权限、任务和问答记录，作为业务真相来源。Redis 用于异步任务、缓存和限流，原文件与解析产物放 MinIO/S3 兼容对象存储。Milvus 仅保存用于检索的向量与索引字段，查询时按研究集合过滤，并由 PostgreSQL 校验访问权限。

RAG 至少需要持续评估：

| 指标 | 要验证的问题 |
|---|---|
| 检索命中率 | 正确证据是否进入 Hybrid 召回与精排后的 top-k 候选 |
| 引用可定位率 | 回答中的引用能否回到用户可检查的位置 |
| 回答受证据支撑率 | 结论是否由引用片段真正支持 |
| 解析成功率 | 不同格式文献是否被可靠转换为可检索内容 |

测试还需覆盖：父块只在数据库提交成功后才更新缓存、文献版本替换时旧向量被清理、一次改写预算不会循环、缺少证据时不生成答案、跨研究集合检索被拒绝，以及复杂问题的每个子问题都保留 trace。

## 9. 待决定的问题

1. MVP 是仅索引开放获取文献，还是同步支持用户上传的 PDF/DOCX？
2. 研究集合是否支持用户手动输入标签、研究问题和笔记？
3. 何种解析质量阈值下允许生成页码级别的引用？
4. 首版是否保存完整问答历史，保存多久，以及用户能否删除？
5. 多 Agent 由哪些问题特征触发，最大允许拆成多少个子问题？
6. 证据核验失败时，前端以何种方式展示“结论未被充分支持”？
