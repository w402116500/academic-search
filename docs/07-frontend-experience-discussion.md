# academic-search 前端体验讨论稿

状态：讨论中，尚未实现。
定位：定义用户如何完成检索、判断结果、建立研究集合并获得有证据的研究回答。
视觉与组件细则见 [`02-frontend-design-system.md`](02-frontend-design-system.md)。

---

## 1. 体验原则

前端不是内部工作流表单，而是面向第一次使用者的研究工具。用户应从一个输入框开始，以渐进披露的方式完成复杂检索，并始终理解系统目前在做什么、结论基于什么证据。

核心原则：

- 搜索框是唯一主入口，不以功能罗列代替真实操作。
- 优先帮助用户做决定，再展示全部元数据和技术细节。
- 长耗时任务必须可见、可解释、可恢复。
- 任何推荐、引用说明和 RAG 结论都可展开查看证据。
- 复制引用优先于下载文件。

## 2. 页面与流程

### 2.1 搜索入口

首屏包含自然语言多行输入框、简短示例和开始检索动作。输入框鼓励用户描述研究场景，而非只填写关键词。

### 2.2 方向选择

系统给出 2-3 张方向卡片。每张卡包含方向名称、简短解释和关键子议题。用户可以选择一个方向，也可以补充说明并重新生成，避免被迫在错误选项中选择。

### 2.3 检索进度

检索页实时展示各 provider 的状态、已发现文献数量、过滤数量和语义评估进度。部分来源失败时要显示失败来源、影响范围和重试入口，而不是静默隐藏。

### 2.4 文献结果流

结果页以可扫描的文献卡片流呈现。卡片默认展示标题、作者年份、来源、相关性摘要、质量信号、官方入口和引用动作；用户展开后再查看完整摘要、推荐理由、证据和题录详情。

结果页还需要提供：排序和基础筛选、单篇加入研究集合、复制 GB/T 题录、打开原文、查看引用说明等动作。“加入研究集合”不是单纯收藏：卡片必须明确显示题录是否为 `ready`、是否有 DOI、正文是否已成功取得。没有 DOI 或正文不可得时保留查看与复制题录功能，但禁用入库动作并说明原因；用户有权处理本地文件时显示 PDF 上传入口。

### 2.5 研究集合与问答

用户进入研究集合后，可查看已加入文献及其索引状态：等待处理、解析中、切块中、嵌入中、可问答或失败。

研究问答界面展示用户问题、回答、引用的证据卡片和原文定位。每条回答中的关键结论都应能跳转或展开到对应片段，证据不足时以明确状态代替貌似完整的回答。

问答运行期间展示可理解的证据轨迹：正在 Hybrid 检索、父块上下文合并、精排、证据核验或等待用户澄清。轨迹只说明系统执行的可验证步骤、候选数量和来源范围，不展示模型的内部思维链。检索不足时，界面按服务端路由展示“补充条件”“选择研究范围”或“当前研究集合证据不足”，并在用户补充后恢复对应任务，而非重新开始整个会话。

## 3. 核心交互组件

| 组件 | 职责 |
|---|---|
| 研究想法输入框 | 承接自然语言输入与示例引导 |
| 方向卡片 | 让用户确认或修正系统对研究意图的理解 |
| 检索进度面板 | 展示 provider、筛选与评估的实时状态 |
| 文献结果卡 | 支持扫描、展开、复制、打开原文和加入研究集合 |
| 引用面板 | 展示标准题录、复制反馈、证据与引用说明 |
| 研究集合列表 | 展示文献、处理状态和失败原因 |
| RAG 证据回答 | 将回答、论文来源、原文片段和定位绑定展示 |

所有图标按钮需有文本提示或无障碍标签；质量等级和相关性不能只依赖颜色；异步加载区域必须预留稳定空间，避免页面跳动。

## 4. 状态设计

每个异步功能都必须定义完整状态，而不只有“加载中”：

| 功能 | 必要状态 |
|---|---|
| 方向生成 | 初始、生成中、可选择、失败、补充后重新生成 |
| 多源检索 | 每源排队、进行中、成功、部分失败、可重试、完成 |
| 文献卡 | 摘要可用、题录补全中、无 DOI、全文待获取、全文下载中、全文校验中、全文不可用、可上传、理由可展开 |
| 研究集合入库 | 正文已验证、等待解析、解析、切块、嵌入、完成、低质量、失败 |
| RAG 问答 | 检索证据、生成中、带引用完成、证据不足、失败 |

对 RAG 问答补充状态：`hybrid_retrieval`、`parent_merging`、`reranking`、`evidence_verifying`、`rewrite_once`、`awaiting_clarification`、`awaiting_scope_selection`。前端以这些稳定状态驱动界面，不根据模型生成文本猜测当前阶段。

无结果、部分失败和低质量解析不能使用泛化错误提示，必须给出用户可理解且能采取行动的说明。

## 5. 响应式与无障碍要求

桌面端是核心工作场景，因为用户通常需要阅读论文和复制引用到写作工具；移动端仍应完整可读、可查看结果和证据。具体断点、字体、颜色、动效与无障碍标准遵循设计系统讨论稿。

关键要求包括：键盘可操作、焦点可见、文字对比度合格、图标按钮具备 `aria-label`、尊重 `prefers-reduced-motion`、中英文混排可读，以及在小屏下不出现横向溢出。

## 6. 待决定的问题

1. 结果页首版需要哪些筛选项：年份、开放获取、文献类型、语言、质量信号？
2. 研究集合是结果页内的侧栏流程，还是独立页面？
3. 移动端是否仅保证查看与提问，还是要支持完整的研究集合管理？
4. 是否需要 SSR 支持公开介绍页和搜索流量，或先以 Vite 单页应用完成工具主流程？
