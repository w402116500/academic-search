# academic-search 前端体验讨论稿

状态：讨论中；静态 HTML 原型和 Vue 主流程页面已实现，并已接入认证、研究计划、检索、候选全文、正式引用与集合构建 API；真实浏览器端到端 Worker 验收和 RAG 研究对话尚未实现。
定位：定义用户如何完成检索、判断结果、建立研究集合并获得有证据的研究回答。
视觉与组件细则见 [`02-frontend-design-system.md`](02-frontend-design-system.md)，逐页状态与跳转规则见 [`10-frontend-interaction-flow-discussion.md`](10-frontend-interaction-flow-discussion.md)。

## 1. 体验原则

前端不是内部工作流表单，而是面向第一次使用者的研究工具。它以“研究指挥台”的方式组织任务：深色控制层呈现工作区与系统状态，浅色阅读层承载文献与证据。用户从一个输入框开始，以渐进披露的方式完成复杂检索，并始终理解系统目前在做什么、结论基于什么证据。

核心原则：

- 搜索框是唯一主入口，不以功能罗列或工作区列表代替真实操作。
- 优先帮助用户做决定，再展示全部元数据和技术细节。
- 长耗时任务必须可见、可解释、可恢复。
- 任何推荐、引用说明和 RAG 结论都可展开查看证据。
- 复制引用优先于下载文件。

## 2. 页面与流程

### 2.1 搜索入口

首屏在深色任务控制面中包含自然语言多行输入框、简短示例和开始检索动作。输入框鼓励用户描述研究场景，而非只填写关键词；最近工作区与数据源可用性只能作为次级信息，不能抢占输入动作。

### 2.2 方向选择

用户提交非空研究要求时先创建 `draft` 工作区并保存原始问题。系统随后将问题显式解析为研究对象、变量、关系或机制、情境、时间范围与语言范围，并给出 2-3 个会影响检索计划的方向选择。用户可以确认、修改或补充说明后重新生成，避免被迫在错误选项中选择；确认后才固化计划并启动检索。

### 2.3 检索进度

检索页以任务时间线和来源状态矩阵实时展示各 provider 的状态、已发现文献数量、过滤数量、相关性评估进度、题录核验和全文获取进度。候选快照在来源规整和基础初筛后立即出现，相关性评估按批次补全；部分来源或模型失败时要显示影响范围和重试入口，而不是静默隐藏；不以“模型思考中”替代可验证的执行状态。

### 2.4 文献结果表与详情检查器

结果页以可扫描、可排序的高密度文献表呈现。每行稳定显示标题、作者年份、来源、相关性层级、DOI 题录状态、全文状态、RAG 状态和主要操作；相关性区域只显示一句“为什么保留”，不展示百分比或技术性命中词。点击行后在右侧详情检查器查看“它主要研究什么”、推荐理由、帮助、局限、建议、证据和题录详情。

结果页还需要提供：排序和基础筛选、单篇加入研究集合、复制 GB/T 题录、打开原文、查看引用说明等动作。“加入研究集合”不是单纯收藏：结果行必须明确显示题录是否为 `ready`、是否有 DOI、正文是否已成功取得。没有 DOI 或正文不可得时保留查看与复制题录功能，但禁用入库动作并说明原因；用户有权处理本地文件时显示 PDF 上传入口。移动端把表格收敛为紧凑可展开行，详情进入底部抽屉。

### 2.5 研究集合与问答

证据研究阶段拆为两个连续页面，不能把集合管理和连续研究对话堆在同一画布中：

1. **研究集合概览**：用户查看已加入文献及其索引状态，包括等待处理、解析中、切块中、嵌入中、可问答或失败；确认当前可回答的文献范围后进入对话。
2. **研究对话**：以连续消息流承载用户问题与带引用的回答。每条助手回答在自身下方按需展开“引用来源”和“检索过程”，其中引用必须显示论文、页码或段落与原文片段；顶部始终显示当前研究集合范围，避免把未入集合记录混入回答。

研究对话页的左侧仅展示**当前工作区内的研究会话历史**，用于在同一研究任务下回看和继续不同问题。跨工作区切换不混入会话列表，而是通过侧栏顶部的工作区切换器直接进入所选任务当前阶段；当前集合摘要仍可直达集合概览。桌面端会话侧栏可折叠为图标栏，窄屏则收起为顶部的工作区切换和会话入口，优先保证对话与输入器的可用宽度。

集合概览中的文献可进入论文详情；论文详情的“在本文内提问”应直接进入研究对话，并自动把检索范围限定为当前论文。研究问答不是普通聊天气泡流，每条关键结论都应能跳转或展开到对应片段，证据不足时以明确状态代替貌似完整的回答。

问答运行期间展示可理解的证据轨迹：正在 Hybrid 检索、父块上下文合并、精排、证据核验或等待用户澄清。轨迹只说明系统执行的可验证步骤、候选数量和来源范围，不展示模型的内部思维链。检索不足时，界面按服务端路由展示“补充条件”“选择研究范围”或“当前研究集合证据不足”，并在用户补充后恢复对应任务，而非重新开始整个会话。

## 3. 核心交互组件

| 组件 | 职责 |
|---|---|
| 研究想法输入框 | 承接自然语言输入与示例引导 |
| 方向卡片 | 让用户确认或修正系统对研究意图的理解 |
| 检索进度面板 | 展示 provider、筛选与评估的实时状态 |
| 文献结果表与详情检查器 | 支持横向比较、排序、筛选、查看详情、复制、打开原文和加入研究集合 |
| 引用面板 | 展示标准题录、复制反馈、证据与引用说明 |
| 研究集合列表 | 展示文献、处理状态和失败原因 |
| RAG 证据回答 | 将回答、论文来源、原文片段和定位绑定展示 |

所有图标按钮需有文本提示或无障碍标签；质量等级和相关性不能只依赖颜色；异步加载区域必须预留稳定空间，避免页面跳动。

## 4. 状态设计

每个异步功能都必须定义完整状态，而不只有“加载中”：

| 功能 | 必要状态 |
|---|---|
| 方向生成 | 初始、生成中、可选择、失败、补充后重新生成 |
| 多源检索 | 每源排队、进行中、成功、部分失败、可重试、完成 |
| 文献卡 | 相关性分析中、已核验理由、信息不足、分析失败可重试、基础初筛跳过、题录补全中、无 DOI、全文待获取、全文下载中、全文校验中、全文不可用、可上传、理由可展开 |
| 研究集合入库 | 正文已验证、等待解析、解析、切块、嵌入、完成、低质量、失败 |
| RAG 问答 | 检索证据、生成中、带引用完成、证据不足、失败 |

对 RAG 问答补充状态：`hybrid_retrieval`、`parent_merging`、`reranking`、`evidence_verifying`、`rewrite_once`、`awaiting_clarification`、`awaiting_scope_selection`。前端以这些稳定状态驱动界面，不根据模型生成文本猜测当前阶段。

无结果、部分失败和低质量解析不能使用泛化错误提示，必须给出用户可理解且能采取行动的说明。

## 5. 响应式与无障碍要求

桌面端是核心工作场景，因为用户通常需要阅读论文和复制引用到写作工具；移动端仍应完整可读、可查看结果和证据。具体断点、字体、颜色、动效与无障碍标准遵循设计系统讨论稿。

关键要求包括：键盘可操作、焦点可见、文字对比度合格、图标按钮具备 `aria-label`、尊重 `prefers-reduced-motion`、中英文混排可读，以及在小屏下不出现横向溢出。
