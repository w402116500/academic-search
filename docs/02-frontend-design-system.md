# academic-search 前端设计系统讨论稿

状态：讨论中。本稿承接 `01-product-direction-discussion.md` §4「前端完全重做」，把方向落成可执行的设计决策。
方法：用 `ui-ux-pro-max` 技能库（50+ 风格、97 配色、57 字体配对、99 条 UX 规则）检索比对，
再按本产品的实际形态取舍。技能推荐不全采纳，采纳与否的理由都记在下面。

---

## 1. 技能库推荐结果与我的取舍

跑 `--design-system` 得到的推荐，逐项判断：

| 维度 | 技能库推荐 | 采纳 | 理由 |
|---|---|---|---|
| 页面模式 | Marketplace / Directory | ❌ 否 | 它按"搜索框 + 列表"的表面特征匹配到了电商目录页。但我们不是撮合买卖双方，没有 listing、没有 host/seller，最后一屏的 "Become a host" CTA 完全无意义 |
| 视觉风格 | Flat Design | ⚠️ 部分 | 扁平、无阴影、快加载的方向对，但 "icon-heavy / bold colors" 不对。见 §2 |
| 配色 | 蓝 #2563EB + 橙 CTA #F97316 | ⚠️ 部分 | 信任蓝的思路对，橙色 CTA 太电商。见 §3 |
| 字体 | Crimson Pro + Atkinson Hyperlegible | ✅ 是 | 命中。见 §4，但有中文问题必须解决 |
| 动效 | 150-200ms、仅色彩/透明度变化 | ✅ 是 | 与"工具型克制"一致 |
| 反面清单 | 避免复杂 onboarding、避免拥挤布局 | ✅ 是 | 正是我们要避免的 |

**结论：技能库的字体和动效建议直接可用，页面模式和配色需要重新选。**

技能库匹配失准的原因值得记一笔：它按关键词（search、directory、listing）做检索，
而我们的产品外形像目录站、内核是分析工具。这类工具的界面参照物应该是
Linear / Vercel / Stripe Dashboard 这类专业工具，不是 Airbnb / Yelp。

## 2. 风格定调：E-Ink 纸感 + 瑞士网格

放弃 Flat Design 的默认推荐，改用技能库里另外两个更贴合的条目组合：

**主风格：E-Ink / Paper**（技能库评级：性能 优秀 / 无障碍 WCAG AAA / 复杂度 低）
```
关键词  纸感、哑光、高对比、阅读、平静、单色
基色    Off-White #FDFBF7 / Paper White #F5F5F5 / Ink Black #1A1A1A
适用    阅读类应用、数字报刊、无干扰写作
```

**结构风格：Minimalism & Swiss Style**（同为 WCAG AAA / 复杂度 低）
```
关键词  网格化、留白、高对比、清晰层级
动效    200-250ms 微妙 hover
适用    企业应用、仪表盘、文档站、专业工具
```

选这个组合的理由：

1. **产品的核心动作是阅读**。用户要读推荐理由、读引用内容、判断这篇论文值不值得看。
   界面本身不该抢注意力。E-Ink 风格的设计目标就是"长时间阅读不累"。
2. **学术语境需要克制**。花哨的渐变、玻璃拟态、强动效会削弱可信度。
   用户在判断"这个工具给的文献靠不靠谱",视觉上的浮夸会直接损害这个判断。
3. **两者都是 WCAG AAA + 低复杂度**。高对比纸感天然满足对比度要求，
   而低复杂度意味着实现快、不容易做坏——对 MVP 很重要。
4. **和旧前端形成明确区隔**。旧界面是 antd 默认观感,辨识度低。
   纸感 + 网格能建立自有视觉语言,不需要重造组件库。

明确不用的风格：玻璃拟态（削弱可信度）、Motion-Driven（性能与无障碍都有代价，
技能库自己标了 `⚠ Prefers-reduced-motion`）、Exaggerated Minimalism（适合作品集，不适合工具）。

## 3. 配色：纸感中性色 + 单一强调色

技能库给的 `#2563EB` 蓝 + `#F97316` 橙是典型 SaaS 落地页配色，橙色 CTA 是电商转化套路。
我们的核心动作是查看证据、复制引用和继续研究，不需要电商式的强视觉推力。

提议的色板（待确认）：

```
背景 底层    #FDFBF7   纸白，主背景
背景 次层    #F5F5F5   卡片、分区
墨色 正文    #1A1A1A   主文本
墨色 次要    #475569   辅助文本（技能库规则：浅色模式下不得浅于 slate-600）
描边        #E2E8F0   卡片边框（技能库规则：不用 border-white/10，浅色下不可见）
强调色      待定       仅用于交互焦点与关键动作
```

强调色的两个候选方向，需要你选：

**方向 A：学术深蓝**（如 #1E40AF 一类的深蓝）
- 传达严谨、可信、机构感
- 风险：与几乎所有学术站撞色，辨识度低

**方向 B：单一非蓝强调色**（如墨绿、砖红、赭石一类）
- 在一片蓝色的学术工具里有辨识度
- 与纸感底色天然协调
- 风险：偏离"信任蓝"的常规认知

我倾向 **B**。理由：产品要在 Google Scholar、Semantic Scholar、Connected Papers
这些全蓝的工具里被记住，而纸感底色配蓝色其实并不好看,配大地色系更自然。

**语义色单独定义**，不参与品牌色：相关性高低、质量等级 A/B/C/D 这些需要色阶，
但技能库有一条规则必须遵守——**颜色不能是唯一指示手段**，
所以等级必须同时有文字标签（"A 级"）和图形（进度条 / 徽章），不能只靠颜色区分。

## 4. 字体：技能库推荐可用，但必须解决中文

技能库的 `Academic/Research` 配对是这次检索里最准的一条：

```
标题  Crimson Pro            衬线，学术感
正文  Atkinson Hyperlegible  无衬线，为可读性专门设计
适用  大学、研究论文、学术期刊
备注  Crimson 用于学术标题，Atkinson 用于无障碍
```

Atkinson Hyperlegible 是 Braille Institute 为低视力用户设计的字体，
刻意加大了易混淆字符（如 I/l/1、O/0）的区分度。对一个要长时间阅读文献信息的界面，
这个选择很到位。

**但有个技能库没提示的硬问题：这两个字体都不支持中文。**

我们的产品面向中文用户，界面文案、中文文献标题、中文引用格式全是中文。
直接用这套配对会导致中文回退到系统默认字体，中英混排会明显割裂——
而学术界面里中英混排是常态（中文说明 + 英文论文标题）。

提议的解决方案（待确认）：

```
英文标题  Crimson Pro
中文标题  思源宋体 Noto Serif SC     ← 与 Crimson Pro 同为衬线，风格可对齐
英文正文  Atkinson Hyperlegible
中文正文  思源黑体 Noto Sans SC      ← 与 Atkinson 同为无衬线
等宽      JetBrains Mono            ← DOI、引用格式等需要精确辨识的字符串
```

用 `font-family` 回退链让浏览器按字符自动选择：
西文走 Crimson/Atkinson，中文走思源。两套都是开源可商用。

未决问题：思源全字重体积很大（单字重 CJK 子集也有数 MB），
需要用 `unicode-range` 分片加载或自建子集。这是个真实的性能成本，MVP 阶段要不要先只加载常用字集？

## 5. 关键界面的具体设计

### 5.1 首屏：搜索框是唯一入口

技能库的反面清单第一条就是"避免复杂 onboarding"。落实为：

```
┌──────────────────────────────────────────────┐
│                                              │
│         说说你想研究什么                       │
│                                              │
│   ┌────────────────────────────────────┐    │
│   │ 比如：区块链在供应链溯源中的应用     │    │
│   │                                    │    │
│   └────────────────────────────────────┘    │
│                          [ 开始检索 ]        │
│                                              │
│   不知道怎么描述？看几个例子 →                │
│                                              │
└──────────────────────────────────────────────┘
```

- 首屏不做功能罗列、不做特性九宫格
- 输入框用 textarea 而非 input：暗示"可以多写几句",这直接影响意图拆解的质量
- 唯一的次级入口是"看例子",降低空白页焦虑

### 5.2 方向选择：卡片式单选

意图拆解的结果用 2-3 张卡片横排（移动端纵排）。每张卡片包含方向名称、
一句话说明、以及该方向下的关键子议题（3-4 个标签）。

关键交互：**允许用户补充说明后再确认**。拆解不可能一次全对,
给一个"都不太对,我再说明一下"的出口比强迫用户在错选项里挑一个好。

### 5.3 检索等待：进度即价值展示

技能库规则 `loading-states` 标为 High 严重度，`progress-indicators` 要求显示多步进度。
但对这个产品，进度条不只是防焦虑，**它是建立可信度的一部分**——
用户看到"查了 5 个源、筛掉 380 篇"才能理解结果是如何产生的。

```
正在检索                                   已用 12 秒
├─ ✓ Semantic Scholar      47 篇
├─ ✓ arXiv                 12 篇
├─ ◐ CrossRef              检索中...
└─ ○ OpenAlex              排队中

元数据过滤   131 → 42 篇
AI 评估      ████████░░░░  28/42
```

技术上用 SSE 推送（单向足够，不需要 WebSocket）。
每个源独立显示状态，某个源失败时明确标注而不是静默跳过——
这既是诚实，也顺带解释了为什么结果数量会有波动。

### 5.4 结果卡片：分层披露

这是产品的核心组件。四件套全展开会让单张卡片过长，10 篇就是一面墙。
技能库规则 `truncation` 给了明确做法：`line-clamp` + 展开。

默认折叠态只显示决策所需的最少信息：

```
┌────────────────────────────────────────────────┐
│ Blockchain-Based Traceability System for       │
│ Agricultural Supply Chain                      │
│ Zhang W, Li M · 2023 · IEEE TII · 引用 156     │
│                                                │
│ 相关性 95  质量 A  ▸ 有实现细节 · 有实验数据    │
│                                                │
│ 直接针对溯源系统架构，提出链上链下协同方案，      │
│ 可作为你第三章的架构参照。                       │
│                                                │
│ [ 引用格式 ] [ 可写入内容 ] [ 原文 ]            │
└────────────────────────────────────────────────┘
```

展开后才显示完整理由、可引用段落、多种引用格式。

三个必须做对的细节：

1. **一键复制优先于下载**。用户的真实动作是把引用粘进 Word。
   复制按钮要有明确的成功反馈（技能库 `error-feedback` 规则的正向版本）。
2. **正文行宽限制**。技能库 `line-length` 规则：65-75 字符。
   推荐理由和引用内容必须包在 `max-w-prose` 里，不能撑满宽屏。
3. **引用内容必须携带出处标注**。这是 §01 里"学术诚信"约束的界面落点——
   生成的段落里必须内嵌 `[1]` 这样的标注，且不可通过复制被剥离。

### 5.5 空状态与失败态

工具类产品最容易忽略的部分,但直接影响留存:

- 检索无结果：给出可操作建议（放宽年份、换个方向、改用英文关键词），不要只说"未找到"
- 部分源失败：显示哪个源失败、结果可能不完整，允许重试该源
- 达到使用上限：说明限制原因与恢复时间，明确下一步可执行操作

## 6. 技术栈确认

在 §01 §4.4 的基础上落定：

| 层 | 选择 | 理由 |
|---|---|---|
| 框架 | Vue 3 + TypeScript | Composition API 适合按功能组织页面与交互状态，并与 Python 后端形成清晰边界 |
| 样式 | Tailwind CSS | 技能库所有风格的 Tailwind 兼容性都是 10/10；避免再出现 4419 行单体 CSS |
| 组件 | Reka UI + shadcn-vue（headless + 可改写） | 面向公众产品需要自有视觉语言，不用 antd 默认观感 |
| 图标 | Lucide Vue | 技能库强制规则：**不用 emoji 当图标**；统一 24×24 viewBox |
| 服务端状态 | `@tanstack/vue-query` | 检索结果的缓存与重试语义天然匹配 |
| 客户端状态 | Pinia | 管理输入草稿、当前方向、卡片展开等不属于服务端的数据 |
| 实时 | SSE | 进度是单向推送 |
| 构建 | Vite | 沿用 |

写进项目规范的硬约束：

```
单文件 ≤ 300 行
必须有 components / views / composables / stores / lib 分层
z-index 只允许 10 / 20 / 30 / 50 四档（技能库 z-index-management 规则）
所有可点击元素必须有 cursor-pointer
过渡时长统一 150-250ms
必须响应 prefers-reduced-motion
断点覆盖 375 / 768 / 1024 / 1440
```

前三条是针对旧前端具体问题的直接反制。

## 7. 交付前检查清单

技能库的清单，加上本产品特有项：

**通用（技能库）**
- [ ] 无 emoji 充当图标，统一使用 Lucide SVG
- [ ] 所有可点击元素有 `cursor-pointer`
- [ ] hover 不引起布局位移（用色彩/透明度，不用 scale）
- [ ] 浅色模式正文对比度 ≥ 4.5:1，次要文本不浅于 slate-600
- [ ] 边框在浅色下可见（不用 `border-white/10`）
- [ ] 键盘导航焦点可见，Tab 顺序与视觉顺序一致
- [ ] 图标按钮有 `aria-label`
- [ ] 表单控件有关联 `label`
- [ ] 响应 `prefers-reduced-motion`
- [ ] 375 / 768 / 1024 / 1440 无横向滚动
- [ ] 异步内容预留空间，避免布局跳动

**本产品特有**
- [ ] 中英混排字体回退正确，中文不掉回系统默认
- [ ] 相关性/质量等级不只用颜色表达，同时有文字与图形
- [ ] 引用内容的出处标注无法被复制剥离
- [ ] 正文行宽受 `max-w-prose` 约束
- [ ] 检索进度中单源失败被明确显示而非静默跳过
- [ ] 复制引用有明确成功反馈

## 8. 需要你决定的问题

1. **强调色方向**：学术深蓝（安全但撞色）还是非蓝色系（有辨识度但偏离常规）？我倾向后者
2. **中文字体加载策略**：思源全量分片加载，还是 MVP 先只做常用字子集？
3. **是否需要 SSR**：影响 SEO 自然流量。工具类产品的落地页 SEO 可能是重要获客渠道
4. **移动端优先级**：手机查文献存在，但复制引用进论文是桌面场景。MVP 是否只保证移动端可读不可用？

前两个问题定了就可以开始搭前端骨架。
