## 1. 已确认的目标链路

```text
用户研究要求
  -> Agent 解析意图并给出方向
  -> 用户确认方向、时间范围与语言
  -> 多源召回
  -> 规整、去重、基础初筛
  -> 形成统一候选集合
  -> 相关性 Agent 对完整集合输出结构化判断与理由
  -> 以相关性优先的稳定分页审核
  -> 用户建立本次准备清单
  -> 每篇文献独立完成题录与全文核验
  -> 用户确认加入研究集合并异步解析、切块、向量化
  -> 受集合范围约束的检索、证据核验与带引用研究回答
```

这里有一条不能混淆的边界：**候选语义判断是集合级任务；文件下载、PDF 校验、入库事务和向量化是文献级任务。**

- 集合级任务需要 Agent 看见同一检索的统一候选，以便做一致的相关性层级、理由和排序判断。
- 文献级任务必须独立处理，因为每篇论文都有不同的 URL、版权状态、文件内容、哈希、对象键和失败原因；它们可受限并发，但不能交给一个 Agent 代替校验或事务。

## 3. P0 已实施的约束

### 3.1 恢复“统一候选集合 -> 一次结构化相关性判断”

目标不是把每篇候选交给独立 Agent，也不是让每批候选互相不知道。实现已让一个已确认检索运行先产生唯一的 `eligible_candidates` 快照，再把必要字段整体发送给相关性 Agent。

Agent 输入只包括：研究问题、已选方向、范围、实际检索词，以及每条候选的 `candidate_id`、标题、摘要、作者、年份、载体、类型、语言和初筛提示。它只能返回评估字段，不能改写题录、DOI、来源或全文状态。

对具备摘要的候选，Agent 输出必须覆盖输入中的全部 `candidate_id`，每条返回：

- `level`：`core`、`related`、`background`、`not_recommended` 或 `insufficient_information`。
- `study_focus`、`reason`、`helpful_aspect`、`limitations`、`recommendation`。
- 仅来自同一候选标题或摘要的原文证据。

容量不是拆分实现的理由，也不再是固定候选数量的阻断条件。完整集合始终一次送入相关性 Agent；相关性判断与独立主张核验的输出 token 预算分别按实际有摘要候选数计算。模型超时、网关拒绝或结构化输出无效才会形成可重试失败，绝不静默退回为多个不具备全局比较能力的串行批次。

### 3.2 恢复“相关性优先”的最终排序

候选仍在分析中时，前端可显示不会跳动的临时顺序；实现中 `completed` 或 `partial_failed` 后，结果 API 使用下列稳定的最终排序键：

```text
相关层级
  -> 同层级内的可解释辅助信号（来源、开放获取、引用量等）
  -> 年份
  -> 标题规范化键
  -> candidate_id
```

游标已绑定排序版本和筛选条件。待评估、失败和跳过记录分别排在五个语义层级之后，避免它们挤占已完成判断的审核顺序；这样既不会在分析中跳页，也不会让最终审核页违背“优先展示最值得读的文献”的产品目的。

### 3.3 同步讨论稿状态

`01`、`05`、`06`、`09` 讨论稿现已只描述已经存在的能力和明确缺口。任务计划可用于推进工作，不能用来掩盖真实代码、接口、测试和线上验收尚未完成的能力。

P0 真实验收已于 2026-08-03 完成：受环境变量保护的真实聊天模型在一次调用中评估 2 条统一候选，逐条标题/摘要证据回链通过；本地 PostgreSQL、Redis、MinIO、Workflow Worker 与真实 arXiv 开放 PDF 的临时候选审核/准入专项也通过。专项测试均使用临时资源并在 `finally` 中精确清理，未读取或修改既有用户数据。

## 4. 后续修改项

### P1：先补齐研究可信度与可用性

| 修改项 | 目标行为 | 验收标准 |
| --- | --- | --- |
| 候选理由二次核验 | 理由中的研究匹配主张不能超出标题/摘要证据 | 伪造或扩大解释的理由被拒绝或降级，不在前端作为确定结论显示 |
| PDF 上传 | 仅允许当前用户、当前候选、用户明确声明有权处理的 PDF 上传到暂存区，再复用既有准入服务 | 不接受任意 URL；校验大小、类型、PDF 魔数、哈希与候选 DOI；上传成功后能进入待确认集合 |
| Reranker | 在 RRF 与父块合并后使用可替换的重排器，或在未配置时明确显示“未启用重排” | `rerank_score` 只有真实计算后才出现；界面和 trace 不把 RRF 截断叫作 Rerank |
| 单轮证据核验 | 回答生成后，将原子主张与实际引用片段送入独立核验节点 | 未被片段支持的主张被删除、降级或转为证据不足；每个保留结论可定位到具体片段 |
| 引用说明决策 | 明确它是否进入 MVP；若进入，只能基于已取得、可定位的正文证据 | 输出不代写、带引用、带限制；否则从页面和讨论稿中标为后续功能 |

### P2：已完成的复杂研究与运行治理

| 修改项 | 目标行为 | 验收标准 |
| --- | --- | --- |
| 复杂问题路由 | 以结构化问题判定替代关键词命中；用户可理解为什么进入复杂模式 | 路由依据、模型与检索预算写入 trace，并有离线图测试 |
| 受限 ReAct | 控制器可基于工具观察决定继续、回答或澄清，工具只限当前集合检索与已授权证据读取 | 每次工具调用、观察和预算均可审计；达到预算后必然回答、澄清或拒答 |
| 运行中取消 | 取消请求写入持久状态，Worker 在节点和外部调用边界协作停止 | 已领取任务确认停止后不写入回答或新证据，并发布 cancelled 终态事件 |
| 配额、预算与指标 | 搜索、入库、复杂/普通研究问答均有用户级 UTC 日限额、全局预算与可观测 trace | 429 返回稳定拒绝原因；入库按实际提交时间和批量文献数预检，研究运行保留预算与阶段耗时 |

真实治理专项在 PostgreSQL、Redis 和当前 Worker 下覆盖了运行中协作停止、终态 SSE、无回答/证据副作用、阶段计时，以及研究问答、搜索和入库的用户/全局日限额。搜索和入库超额均在调用队列前拒绝；`ingestion_runs.submitted_at` 只在 `pending -> queued` 或失败重试的新运行写入，因此未确认构建的文献不会占用额度。

## 5. 不应误改的部分

以下设计已经符合产品边界，整改时不得为了“批量化”而绕过：

1. 未通过 DOI、题录和正文三重条件的候选，不写入长期 `papers`，也不能进入 Milvus。
2. 全文下载、PDF 校验、对象转正、入库和向量化按文献独立处理；批量操作只负责调度、汇总状态和有限并发。
3. RAG 只能在当前用户、当前研究集合、当前文档版本内检索；Milvus 过滤不是唯一权限依据，PostgreSQL 必须二次校验。
4. 候选理由只能基于标题/摘要；全文片段只属于后续 RAG 证据，不能被候选推荐理由伪装为已经阅读。
5. 不爬出版商落地页，不绕过付费墙、登录、验证码或版权限制。
