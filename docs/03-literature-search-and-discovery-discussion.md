# academic-search 文献检索与发现讨论稿

状态：研究入口、多源候选检索、标题摘要相关性评估、候选审核工作台、全文准入、集合构建与 RAG 入库后端已实现。候选理由由标题/摘要相关性 Agent 在完整统一候选集合的共享上下文中产生；首轮中单条模型结果无效不会抹掉已核验同伴，只会触发未解决候选的一次集合级重试。候选能否进入研究集合仍由 DOI、正式题录和已验证全文的确定性规则决定。整改约束见 [`11-implementation-alignment-discussion.md`](11-implementation-alignment-discussion.md)。
定位：定义用户从描述研究想法，到获得一组可信、可排序的候选文献的完整流程。
关联：产品总方向见 [`01-product-direction-discussion.md`](01-product-direction-discussion.md)；结果呈现见 [`04-literature-results-and-citation-discussion.md`](04-literature-results-and-citation-discussion.md)。

---

## 1. 要解决的问题

目标用户通常知道自己想研究什么，却不知道如何把想法拆成有效关键词、如何判断一篇论文是否真的相关，也无法在多个数据源之间判断题录是否可信。

本模块的输入是自然语言研究描述，输出是一组经过筛选、排序且能追溯来源的候选文献。它不是“返回一堆搜索结果”，而是帮助用户完成第一次研究方向收敛。

候选文献不等于可供 RAG 研究的文献。Provider 在这一阶段只返回题录元数据和可能存在的全文链接；系统尚未下载、验证或保存正文。

## 2. 用户流程

```text
输入研究想法
  -> Agent 拆解研究意图
  -> 返回 2-3 个候选研究方向
  -> 用户选择方向，并可补充限定条件
  -> 多源召回候选文献
  -> 元数据过滤、去重与基础初筛
  -> 标题与摘要相关性 Agent 评估
  -> 高相关候选题录预取 / 用户动作按需补全
  -> 以稳定分页审核候选并建立本次准备清单
  -> 批量准备题录与全文核验
  -> 将通过准入的候选加入待确认集合
  -> 用户确认后构建可研究集合
```

首版只做这一轮“输入 -> 方向选择 -> 检索”的引导，不把多轮对话式选题澄清作为前置依赖。

## 3. 功能需求

### 3.1 研究意图拆解

- 用户可以用自然语言输入问题、研究对象、场景、方法或预期目标。
- 系统将输入拆为研究主题、对象、关系、约束条件和可检索的概念。
- 系统生成 2-3 个候选方向；每个方向包含名称、一句话说明和关键子议题。
- 用户可以选择一个方向，也可以补充说明后重新生成方向。
- 确认方向后，系统生成面向不同学术数据源的查询表达式。

方向选择是用户校正系统理解的关口。检索不能在用户尚未确认系统理解之前直接开始。

### 3.2 多源候选召回

MVP 接入以下来源：

| 来源 | 在流程中的职责 |
|---|---|
| OpenAlex | 候选发现、开放获取状态与可能的全文 URL |
| Semantic Scholar | 候选发现、摘要、引用量等学术元数据 |
| CrossRef | DOI 与正式题录补全 |
| arXiv | 预印本与新近研究线索发现 |

每个来源独立执行、独立报告状态。某一来源失败时，其余来源继续完成，并将结果不完整性明确传递到前端。

题录可信度采用来源分级：正式题录应优先由 Semantic Scholar、CrossRef 或 OpenAlex 等正式学术元数据来源确认；arXiv 只作为发现线索，不能单独承担正式题录的依据。

### 3.3 候选处理与筛选

候选文献进入排序前必须依次完成：

1. 规范化标题、作者、年份、DOI、URL、来源等元数据。
2. 识别同一论文的跨源重复记录并合并来源信息。
3. 过滤非正式站点、明显不符合文献类型要求的内容和基础条件不满足的候选。
4. 先发布已统合候选快照；题录初始状态只说明当前是否已就绪，不阻塞候选展示。
5. 对通过初筛的完整候选集合进行一次相关性评估：具备摘要的候选由模型在共同上下文中判断，缺摘要候选由服务端确定性标为信息不足；已核验的正向结果立即保留，单条无效、缺失或无法核验的模型结果只使对应候选进入一次集合级重试；核心相关、关联研究和背景参考候选可在限额内预取题录，其余仅在用户打开详情、复制引用或加入集合时按需补全。

元数据过滤必须先于模型评估，以减少模型成本，也避免让低质量候选进入最终结果。题录核验与语义评估是两条不同的处理线：题录决定能否复制正式引用和进入研究集合，语义评估解释候选为什么值得审核。结果页不能等待所有 DOI 请求完成才展示统一候选。

### 3.4 相关性排序

排序的主键是与用户已确认研究方向的相关性。质量、时效性、全文可得性等只作为次级信号或筛选条件，不应掩盖用户真正的研究意图。

首版需要为每篇文献记录并可展示以下信号：

| 信号 | 用途 |
|---|---|
| relevance | 主排序依据，表示论文与研究意图的匹配度 |
| quality signals | 来源、引用量、同行评审信息等可解释原始信号 |
| recency | 年份与是否属于综述类文献 |
| utility | 是否有方法细节、代码、数据或实验信息 |
| accessibility | 是否可访问全文、语言与篇幅信息 |

不在 MVP 中把不同学科的期刊等级、引用量强行压缩成一个看似精确的“质量分”。原始信号和计算依据应保留给用户判断。

标题摘要评估应返回结构化结果，而非仅返回“相关/不相关”：至少包括相关层级、主要研究内容、可解释理由、所依据的标题/摘要原文、局限和建议动作。相关层级固定为 `core`（核心相关）、`related`（关联研究）、`background`（背景参考）、`not_recommended`（不建议优先）和 `insufficient_information`（信息不足），它们不是论文质量分数。

评估只读取用户确认的研究问题、方向、时间/语言范围、实际检索词和统一候选的公开元数据；它不能读取或声称读过全文，也不能改写 DOI、作者、来源或题录。模型传输层采用扁平 JSON，服务端先完整聚合流式 JSON，再转换为稳定业务契约，并核验每个证据摘录确实存在于同一候选的标题或摘要。无摘要候选直接标为信息不足，未通过基础初筛的候选标为跳过；模型输出异常或暂不可用时不会回退到关键词匹配理由。首版不展示虚假的百分比置信度。

已确认的实现约束如下：

1. 一次检索先完成规整、去重和基础初筛，形成唯一的统一候选集合；相关性 Agent 首次接收这一集合的必要字段，在共享上下文中返回带 `candidate_id` 的结构化判断。服务端逐条验证返回项、证据和理由：有效同伴立刻合并；仅无效、缺失、重复或无法核验的候选构成一次重试子集。不得为了展示进度而把首轮集合隐式拆成互不知情的串行小批，也不得因一条无效记录把整批标为失败。
2. 最终审核列表只展示通过证据核验的 `core -> related -> background` 正向候选；同一层级内再使用可解释的质量、时效性和稳定标题键作为次级排序。`not_recommended`、`insufficient_information`、不受支持的理由和耗尽重试的技术失败只保留短期审计，不占用用户筛选、准备清单或后续准入。候选仍在分析时可保持稳定快照，但不能把“稳定分页”变成最终按年份排序的理由。
3. 推荐理由的证据校验至少分两层：先确认引文逐字存在于同一候选标题或摘要，再确认“为什么推荐”的结构化主张没有超出这些元数据能够支持的范围。只校验字符串存在并不足以证明理由可靠。
4. 当前模型容量足以承载完整统一候选集合，系统不得以固定候选篇数阻断相关性判断。仅当实际输入或预留输出限制要求时才使用有界批次；首轮始终保留完整集合语境。外层 JSON 为空、截断或不可解析时，当前调用中的全部未解决候选作为一次重试子集；逐条校验失败时只重试失败项。第二次尝试只接受与当前 `PENDING` 候选精确一致的私有重试 ID 集合，任何缺失或外来 ID 都回退到全部待处理项，确保不会有候选静默遗留。耗尽重试后，只排除该子集，绝不重算或排除已落定同伴。

### 3.5 检索进度与失败处理

- 后端以 SSE 向前端单向推送检索、筛选和评估状态；候选快照先可见，模型流在服务端聚合、解析和校验后才写回同一会话，浏览器不会接收未经验证的模型片段。
- 进度事件至少包含数据源状态、发现数量、过滤数量、相关性总数、已完成数、失败数和可恢复错误。
- 用户可看到“正在做什么”，而不是只有一个无解释的加载图标。
- 可重试的 provider 失败、限速和网络错误应记录原因并按策略重试；可重试的相关性输出失败只重试当前未解决子集，并使用 Redis 租约锁避免重复调用模型。技术失败在重试耗尽后转为内部可审计的不可展示结果，用户继续审核已验证的正向候选。候选数量本身不是相关性失败原因，也不得要求用户仅为绕过数量阈值而缩小检索。

### 3.6 全文获取与研究集合准入

用户点击“加入研究集合”后，系统才对该候选启动全文获取流程。首版采用严格准入：候选必须同时满足以下条件，才会成为可长期保存、可向量化的研究文献。

1. 存在 DOI，且通过 DOI Content Negotiation 或权威来源补全后，题录状态为 `ready`。
2. 系统已实际取得一份允许处理的全文，而不是只拿到论文落地页或 PDF 链接。
3. 全文通过下载、类型、大小、内容完整性和来源权限校验，并被安全保存到私有对象存储。

无 DOI、题录为 `partial`、`conflict` 或 `unresolved` 的候选，仍可在结果页展示，但不能加入研究集合、写入 PostgreSQL 或进入 RAG。存在 DOI 但未能合法取得正文的候选同样不能入库；系统应明确提示“可查看或复制题录，但当前不可用于文献研究”。

首版的可获取范围刻意收紧：

- 自动获取：仅处理 Provider 已明确标为开放获取、且给出直接 PDF URL 的候选。
- 用户上传：目标行为是接受用户确认有权处理的 PDF；当前尚未提供上传入口，见整改稿 P1。
- 不做：不爬取出版商落地页、不绕过登录、付费墙、验证码或访问限制，也不将第三方论文库作为下载来源。
- 后续扩展：对已配置且明确许可的官方来源，可增加 `official_download`；HTML、DOCX 的自动获取与解析另行设计。

自动获取必须作为受控异步任务执行。后端只能使用 Redis 搜索会话中已发现的全文 URL，不能接受前端提交的任意下载地址；下载时需限制重定向、单次网络等待、整次获取总时限与文件大小，并同时校验 HTTP `Content-Type` 与 PDF 文件魔数。每次重定向都要阻止访问私有网络地址，避免 SSRF。下载成功后计算 SHA-256，先写入临时对象；准入服务将暂存对象服务端复制为正式对象，再在单个事务中创建论文、工作区关联、文件记录和初始入库运行。对象存储与数据库不能构成单一事务，因此任何一步失败都必须补偿删除正式对象和暂存对象。

当前已实现 `app/modules/documents` 的下载与暂存边界：它只接收已规整的内部候选对象，拒绝未完成 DOI 题录核验、非开放获取或没有直接 PDF URL 的候选；对每一跳重定向重新执行 HTTPS、端口和公网地址校验，并流式验证 PDF 后上传至 `staging/fulltext/`。

当前已实现 `app/infra/db/repositories/literature_admission.py::SqlAlchemyLiteratureAdmissionAdapter`：它复核候选、`ready` 题录与暂存 PDF 属于同一 DOI，校验当前用户对活动研究集合的所有权，处理同一 DOI 的幂等重复加入，并将对象转正。在一个 PostgreSQL 事务中创建或复用 `papers`，再创建 `collection_papers`、`documents` 与状态为 `pending`、阶段为 `parse` 的 `ingestion_runs`；数据库或对象操作失败时会清理正式键和暂存键。`POST .../fulltext/admission` 已接入该服务，但它不会自动投递 Worker。用户调用 `POST /collections/{collection_id}/build` 后，集合构建服务才将活动 `pending` 运行批量切换为 `queued` 并逐篇投递 arq；单篇队列失败会明确写为 `failed`，不影响已投递的文献。`app.workers.ingestion` 消费 `queued` 运行并完成 PDF 解析、切块、embedding 与 Milvus 写入。成功结果仍只表示“文献已进入研究集合并等待或正在入库”，只有 `completed + is_current=true` 才表示能够被 RAG 检索。

全文下载默认直连且不读取进程级 `HTTP_PROXY` / `HTTPS_PROXY`。某个开放获取来源在当前网络环境无法直连时，可显式设置 `FULLTEXT_NETWORK_MODE=proxy`，它只复用已校验的 `LITERATURE_PROXY_URL`，不会改变 MinIO、数据库或其他服务的网络路由。

检索阶段中的全文状态只保存于 Redis 或任务状态，不建立长期候选表：

```text
not_available -> queued -> downloading -> validating -> available
                                              |
                                              -> requires_upload / failed
```

`available` 仅表示文件已获取、校验并写入私有暂存区；后续“加入研究集合”服务创建文献文件记录和 `pending` 入库运行。用户可在构建前从集合中移出该文献，此时系统归档关联并取消运行，但不立即物理删除正式对象，避免对象存储与数据库跨服务删除不一致。只有用户明确确认构建集合后，运行才会进入 `queued`，Worker 实际完成解析、切块、嵌入和索引后，该文献才可被 RAG 召回。

### 3.7 候选审核与集合准备

候选结果不是“勾选后立刻入库”的收藏页，而是一段有明确边界的审核流程。系统区分四层对象：

| 层次 | 保存位置 | 用户可见含义 | 生命周期 |
|---|---|---|---|
| 正在查看 | 浏览器前端 | 当前在右侧检查器或详情页阅读的候选 | 页面交互状态，切换行即可改变 |
| 本次准备清单 | Redis，归属当前 `search_run` | 用户希望统一核验、再决定是否纳入的一批候选 | 与搜索会话 TTL 同步过期 |
| 待确认集合 | PostgreSQL | 已有 DOI、正式题录和已验证全文，等待用户确认构建的一批文献 | 持久化，直到移除或开始构建 |
| 可研究集合 | PostgreSQL + Milvus | 已完成当前版本解析、切块、嵌入与索引，可作为 RAG 证据的范围 | 持久化版本状态 |

结果 API 使用服务端稳定排序的游标分页，支持关键词、中文/英文、相关性、开放获取、DOI、全文状态和“只看已选”等筛选。前端点击结果行只改变“正在查看”，复选框才更新本次准备清单；二者绝不互相隐式改变。

准备清单只接受当前搜索会话中存在、通过基础初筛且有 DOI 的候选。批量“准备核验”逐篇复用单篇全文服务：Worker 可按需补齐题录，再下载、校验和暂存开放获取 PDF。批量“加入待确认集合”只接收全文状态为 `available` 的记录，并复用准入服务创建 `papers`、`collection_papers`、`documents` 和 `pending ingestion_runs`。任一项失败只阻断该项，其他候选继续处理；批量操作的“已投递”不表示正文已经可用于 RAG。

本次准备清单随 Redis 搜索会话过期，不创建候选收藏或候选评价等长期表。搜索会话过期后，用户应重新检索；已进入待确认集合或可研究集合的持久化数据不受影响。

## 4. 核心数据与状态

检索会话至少关联：原始用户输入、方向候选、已确认方向、查询表达式、provider 调用记录、候选文献与处理阶段。

每篇候选文献保留独立阶段状态：`triage -> citation -> fulltext -> reader`。不同阶段的成功、失败和错误原因必须分别记录，便于重试、审计和前端解释。`fulltext` 成功仅在文件已实际获取、校验和保存后成立，不能因拥有落地页或猜测性 PDF 链接而标记成功。

其中 `citation` 阶段只在用户复制引用或将候选加入研究集合时按需执行：先请求 DOI 的 CSL-JSON，再只补全候选缺失字段；已有值与 DOI 结果不一致时记录冲突，绝不静默覆盖。该阶段不参与预印本过滤，arXiv 等发现线索仍会保留在候选结果中；但 arXiv 的 PDF 只有同时具备 DOI 题录核验时，才可能进入研究集合。

## 5. 成功标准

- 用户能在首次使用时完成从想法到方向选择，不需要学习复杂检索语法。
- 结果中的题录来源可追溯，跨源冲突不被静默覆盖。
- 相关性排序能让用户优先看到值得阅读的文献，而非仅满足固定篇数。
- 单个数据源失败不会导致整个检索会话失败。
- 进入 RAG 的每篇文献均能回溯到已核验 DOI 和已经取得、校验过的正文文件。

## 6. 待决定的问题

1. 每次检索默认展示多少篇结果，何时提示用户缩小或扩大范围？
2. 质量信号首版展示到什么粒度，是否先只显示来源、年份、引用量与开放获取状态？
3. 中文文献源在哪个版本进入，采用开放来源还是商业数据服务？
4. 用户补充说明后，是重新完整检索，还是支持在原结果上增量筛选？
