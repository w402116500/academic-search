# 技术设计：候选自动核验、研究集合与 RAG 范围

## 目标与边界

本任务把当前的“Redis 准备清单 -> 用户准备全文 -> 用户确认构建 -> RAG”改为两条
独立的事实链：

1. `modules/search` 拥有短期候选审核快照和一次性的自动题录/PDF 可得性结果；
2. `modules/research` 拥有用户确认保留的全部集合书目条目；
3. `modules/documents` 拥有受控 PDF 探测、下载、上传和文件身份校验；
4. `modules/rag/ingestion` 只接收实际取得的 PDF，完成后才把条目放入 RAG 研究范围。

现有 `Paper` 仍是已核验的全局规范题录事实，不能再承担“用户选择了一条候选书目”
这一较弱事实。现有 `Document` 需要能关联集合书目条目，即使该条目尚没有可用的
`Paper`。这避免用伪造引用、伪 DOI 或共享论文记录来保存用户选择。

本任务不实现 Redis 候选快照的持久恢复，不改 Fast/Strict RAG 的回答交互，不改工作区
永久删除任务已拥有的删除围栏。研究聊天中的范围详情继续消费已有的 RAG 文献列表；
本任务仅扩展集合 API 以提供全部书目条目。

## 持久化模型与迁移

新增研究所有的 `CollectionBibliographyEntry`，一条记录对应一次用户将候选加入研究集合。
它至少保存：所属集合、来源 search run/candidate ID、候选展示元数据快照、题录快照与
稳定题录状态、PDF 可得性、内容处理状态、自动下载次数、可选的 `paper_id` 和
`document_id`。唯一键为集合与来源候选的组合，重复点击返回同一条目。

`CollectionBibliographyEntry` 是“研究集合”的计数来源；`Document + current completed
IngestionRun` 是“RAG 研究范围”的计数来源。前者可以没有 PDF，后者必须有已完成索引。

为让没有正式引用的条目也能进入 RAG：

- `Document` 增加不可变的集合书目条目关联；新文档以它作为归属和删除边界。
- 现有 `paper_id` 保留为可选的规范元数据投影。题录为 `ready` 时可创建/关联共享 `Paper`；
  题录不可用时不创建伪造 `Paper`，但有效 PDF 仍可入库。
- 读取、检索和证据组装从条目取得标题、作者与来源元数据；有 `Paper` 时优先使用其已核验
  字段。正式引用只在条目的题录状态为 `ready` 时返回文本。
- Alembic 新 revision 先创建条目表和可空关联，再为历史 `CollectionPaper`/`Document`
  回填对应条目及关联。代码切换到新关联后才为新写入要求条目关联；不得原地改既有 revision。

集合列表响应新增 `bibliography_entries` 和“集合书目数 / RAG 可研究数”摘要字段；保留
现有 `documents` 字段作为已经取得 PDF 的文档列表，降低范围详情任务的兼容风险。

## 自动候选就绪链路

相关性评估完成后，`CandidateRelevanceRunExecutor` 进入候选就绪阶段，而不是只对前 N 篇
调用 `_enrich_citations`：

```text
相关性完成
  -> 候选审核池全部候选
  -> 题录解析 + 公开 PDF 探测（各自受限并发、逐项隔离、至多一次自动重试）
  -> 原子合并 Redis 候选快照
  -> SearchRun 完成，开放候选审核
```

题录调用复用 `CitationMetadataEnricher`，删除固定预补全上限。每个候选都会留下稳定的
`ready` 或不可用状态；解析、冲突、限流等细节只进入结构化日志，不进入页面文案。

`modules/documents` 增加只读的公开 PDF 可得性探测器。它只接受候选提供的明确 PDF 地址，
复用受控 URL/重定向/公网地址策略，以 HEAD 或有严格字节上限的请求确认可访问性；它不下载、
不暂存、不开启解析。探测结果只为 `available` 或 `requires_upload`，并保留可供后续下载的
安全来源地址。题录状态不再是 PDF 探测的前置条件。

任一候选的 Provider 或网络故障不能丢弃其余候选。完成时每个审核候选都有题录和 PDF 状态，
`SearchRun` 的新阶段/计数明确表示正在自动就绪或已经完成。日志使用 run ID、candidate ID、
阶段和稳定错误码，禁止记录 Provider 原始响应、上传内容或凭据。

## 加入集合、下载与入库

候选页保留 Redis 多选，但只保留一个持久化命令：加入研究集合。

1. `CandidateAdmissionService` 改为对所有已选候选创建或读取集合书目条目，不再读取
   `CandidateFulltextState`，不再因 DOI、题录或 PDF 状态产生“blocked”。成功条目才从
   Redis 选择清单移除。
2. PDF 探测为 `available` 的条目在提交后写为待自动获取，并投递集合条目下载任务；其余条目
   直接写为 `requires_upload`。队列投递、下载或文件校验失败由系统自动再尝试一次，第二次
   仍失败才转换为 `requires_upload`。
3. 下载和上传共用 PDF 校验、暂存和提升流程。新增 PDF 身份检查：当 PDF 中可提取 DOI 或标题
   且其与候选明确冲突时拒绝；未提取到标识不构成拒绝。该检查不要求题录已 `ready`。
4. 有效 PDF 提升为 `Document` 后，在同一持久化状态机中创建并投递 `IngestionRun`。上传入口
   改以持久化集合书目条目 ID 为对象，因此候选 Redis 会话过期后仍可上传；上传成功无需
   第二次“确认构建”。
5. Worker 每个安全边界检查条目/集合是否仍有效。集合条目被移除时，取消或终止其下载、入库，
   精确删除对象、解析数据、向量和入库运行；共享 `Paper` 不作为删除目标。

旧的候选“准备核验”、单篇/批量重试、候选全文准入和“确认并构建集合”命令不再是产品入口。
路由、OpenAPI 和前端 API 层一起移除或替换，避免保留可绕过新状态机的隐藏用户路径。

## API 与前端呈现

候选审核响应为每项返回题录状态与 PDF 可得性。前端只映射为以下稳定文本：

- `题录已核验` 或 `该题录暂不可用`；
- `可自动获取 PDF` 或 `需上传 PDF`。

`ResultsView` 继续使用现有工作区壳、三阶段导轨、紧凑候选行和右侧检查器：

- 候选行不再因 DOI 或题录未就绪而禁选；
- 检查器标题改为“文献详情”，依次显示正式引用（仅 ready）、PDF 状态和相关性依据；
- 删除“准备单篇核验”“前往核验任务加入集合”和技术处理记录的失败明细；
- 多选后唯一主命令为“加入研究集合（X）”。

`CollectionView` 改为两块固定信息：左侧显示全部研究集合书目及每篇的 `已进入 RAG`、
`正在入库` 或 `需上传 PDF`；右侧固定显示 RAG 研究范围数量、仅范围内文件会被问答使用的
状态，以及 PDF 上传入口。只要范围数量大于零，研究对话可用。用户可删除集合书目条目，
但不获得题录/PDF 的手动重试按钮或内部失败原因。

前端只使用 OpenAPI 生成 DTO、TanStack Query 失效与轮询持久化集合状态；不把下载或完成状态
复制到 Pinia。任何 API 变更都同步生成 `openapi.json` 与 `schema.ts`。

## 兼容、风险与回滚

- 旧 Redis 搜索会话保持其现有 TTL 行为；会话过期不会影响已经加入集合的条目，但仍无法恢复
  未加入的候选审核列表。
- 历史集合通过 migration 回填为书目条目，已有已完成文档继续是 RAG 范围，不触发重新下载或
  重新入库。
- 外部 PDF 的可得性只能是受限探测结果，真正的文件可用性仍由加入集合后的下载和验证决定。
  因此 UI 只承诺“可自动获取”，不承诺已经取得。
- 该变更同时触及数据库、API、两类 Worker、对象存储、向量清理和前端。发布前必须先执行
  migration 升级和契约测试；回滚代码前需确认新条目数据的读取兼容性，不能通过删除数据回滚。

## 相邻任务协调

- `08-07-research-scope-document-details` 保持消费 `documents`，用于显示已入库范围；本任务
  新增的 `bibliography_entries` 不改变其打开/关闭抽屉交互。
- `08-07-rag-answer-reading-citations` 继续只消费 RAG 范围内的证据，不能把无 PDF 的书目混入
  引用来源。
- `08-07-permanent-workspace-deletion` 的集合删除围栏是所有新条目 Worker 的前置条件；本任务
  的单条目删除复用同一对象/向量清理端口，不重做工作区级删除状态机。
