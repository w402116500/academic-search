# 工作区永久删除

## Goal

允许用户永久删除工作区及其私有数据，避免无用工作区持续占用数据库、对象存储和向量索引。

## Requirements

- 左侧工作区列表中的每个可用工作区提供删除入口；避免误触，先打开二次确认对话框。
- 确认对话框必须展示工作区名称并明确提示“删除后无法恢复”；不要求用户输入名称，不提供归档或回收站。
- 用户确认后，后端必须先持久化封锁工作区的新写入，取消该工作区的未完成搜索、相关性、全文、入库和研究任务，并等待它们全部达到终态。
- 只有删除屏障通过后，后端才能删除工作区私有对象、按 ingestion run 删除向量并物理删除数据库关联记录。
- 共享的 `Paper` 事实不能因一个工作区删除而被误删。
- 任何清理失败或任务未终态时，API 不得返回成功；工作区应保持不可写且标记为
  `deleting`，所有者能在左侧列表和研究入口的“待完成删除”区域继续删除。
- `deleting` 工作区不可导航、不可研究、不可编辑；继续删除无需再次进行不可恢复确认。
- 删除失败向用户展示统一、非技术性的提示；具体错误原因仅写入后端安全日志。
- 成功删除后，前端失效相关查询缓存；若删除当前工作区，跳回研究入口，不能继续渲染已删除路由。

## Acceptance Criteria

- [ ] 用户在左侧工作区列表可发起删除，并必须经过展示名称和不可恢复警告的第二次确认。
- [ ] `DELETE /api/v1/collections/{collection_id}` 仅删除当前用户拥有的工作区，其他用户或不存在资源返回统一的 404 语义。
- [ ] 删除动作封锁新写入并等待已运行任务终态；运行中 Worker 不会在清理完成后向已删除工作区写入持久记录、对象或向量。
- [ ] 所有该工作区 ingestion run 的向量、私有文档对象和级联数据库记录均被清理，且共享论文记录保留。
- [ ] 外部存储、向量或数据库私有记录清理失败时不返回成功，并保留可恢复的服务端删除状态。
- [ ] `deleting` 工作区对所有者可见但不可打开，侧栏和研究入口均可继续删除，且不泄露底层故障细节。
- [ ] OpenAPI 产物、前端 API hook、查询缓存和路由跳转与新 API 同步；测试覆盖服务层状态机、路由所有权和前端确认/成功路径。
